# Advanced V2 reports and provenance

V2-17 adds an opt-in semantic intelligence report and portable archive on top of
the V2-15 provenance contract. [V2 analysis commands](cli.md#v2-analysis-commands) expose the native engines as explicit stages. [V1 reports](reports.md) retain their existing sections and legacy
schema-1 support. [Artifact lineage](run_artifacts.md#v2-artifact-lineage-opt-in)
defines the DAG, bounded local reads and integrity decisions.


## Generate an advanced report

```sh
python examples/advanced_report.py --out runs/v2/report-proof
python examples/advanced_report.py --without-optional --out runs/v2/report-absent
# Regenerate a verified schema-2 bundle with captured native analyses:
dvi report runs/v2/report-proof --advanced --overwrite --json
```

The example executes the real local harness, ontology/intent, representation,
temporal, oracle, counterfactual, statistical, graph and shrinking engines. It
records nine missed and two detected variants; oracle consensus remains
`not_enough_evidence`, shrinking stops as `unknown`, and confidence is
`insufficient_sample`. A measured miss does not manufacture consensus or a minimum.
The absent-analysis example retains all sections and labels missing evidence.

`build_reports(..., advanced=True)` returns the generated bytes;
`write_reports(..., advanced=True)` publishes through the existing verified atomic
writer. Advanced reports require a schema-2 bundle with its provenance DAG.
A schema-1 input is rejected; follow the migration procedure below first.
Once a report is schema 3, subsequent regeneration preserves its format even when
`--advanced` is omitted. Legacy schema-1/2 serialization and rendering are unchanged.

Outputs are `report.html`, `report.md`, `report.json`, `report_bundle.zip` and
`report_assets/report.css`, alongside the retained evidence, provenance and manifest.
Open `report.html` locally with its neighboring files. There is no JavaScript, CDN,
remote font or remote resource. HTML text is autoescaped, Markdown text is escaped,
and generated links use fixed local names or validated portable manifest paths.
Commands are inert text, never executed by report generation.

## Reading the report

The opening counts, Executive Summary, Fragility Frontier and Recommendations
form a short review route; tables retain at most 20 rows and link to full evidence.
The summary reports actual confidence classes, not just whether statistics ran.
Detailed review takes longer than the overview. The eighteen required sections are:

1. Executive Summary
2. Scenario and Inputs
3. Semantic Signal
4. Detection Intent
5. Schema/Profile Mapping
6. Temporal and Correlation Evidence
7. Oracle Consensus
8. Fragility Frontier
9. Counterfactual Explanation
10. Minimal Reproducer
11. Statistical Confidence
12. Knowledge Graph Summary
13. Weak Edges
14. Recommendations
15. Limitations
16. Reproduction Commands
17. Artifact Provenance
18. Safety Boundary

The machine document retains the existing run/frontier/provenance contract and an
`advanced` object of strict native models. `null` means an optional analysis was not
supplied; a present `unknown` result means it ran without resolving its evidence.
Neither is a pass. Legacy probes, differential comparisons and minima remain
explicit and do not acquire V2 oracle claims.

## Evidence scope and verification

| Section input | Primary artifact | Required relationship |
| --- | --- | --- |
| Semantic signal | `normalized_events.jsonl` | Re-extracted using the default ontology from the verified baseline. |
| Detection intent | `semantic_loss_report.json` | Recomputed event support from the retained declaration and baseline. |
| Schema/profile mapping | `metamorphic_report.json` | Retained source is a baseline event; projections and comparisons are reproduced. |
| Temporal/correlation | `temporal_summary.json` | Exact baseline event coverage and ordered event hashes; aggregate state matches recorded checks. |
| Oracle consensus | `oracle_consensus.json` | Retained case, expectation and observation match the run; decisions are reproduced. |
| Counterfactuals | `counterfactual_summary.json` | Baseline, harness, policy, expectation and seed match the run. |
| Statistics | `confidence.json` | Current canonical snapshot and its event/observation proofs match; native numerical validators rederive estimates. |
| Knowledge graph | `detection_graph.json` | Reproduced graph has the matching captured counterfactual study as its source. |
| Oracle-aware minimum | `shrunk_case.json` | Original events, case, policy, expectation and harness match the run. |

Producers must declare extra artifact parents through the existing lineage API.
The report does not assign meaning to arbitrary extra filenames. Supporting native
views can also be retained; rendered claims use the primary models above. The
example renames the V2 shrinking trace to `oracle_shrinking_trace.jsonl` because
`shrinking_trace.jsonl` belongs to the legacy `minimal_case.json` contract.

Every generation begins with full bundle verification and rechecks captured source
hashes. Schema-3 verification also compares the report's run, frontier, provenance,
regression and optional analyses against actual evidence, then checks exact
renderings, stylesheet and archive bytes. Rehashing a changed presentation or
unrelated native analysis cannot make it a valid report. Safety rejection in a
native input blocks advanced rendering.

The temporal summary retains recorded predicate results; report generation does
not reconstruct its original window/pattern settings or replay a detector. Native
counterfactual and shrinking evidence retains the producer's bounded observations.
Hash verification is consistency, not authenticated authorship or independent
execution. Statistical cohorts can retain other seeds/historical runs, with the
current run explicitly linked. Graph remedies remain untested proposals.

## Deterministic portable archive

The outer bundle manifest/DAG covers the ZIP as a derived report artifact. The ZIP
contains all evidence, reports and assets plus its own canonical manifest and DAG,
but no nested ZIP. Extracted contents pass the ordinary `verify_artifacts` check and
all provenance links resolve locally. This avoids a manifest/archive hash cycle.
Its inner manifest digest intentionally differs from the outer bundle's digest.
Regenerating the extracted bundle can add a new outer ZIP without changing evidence.

Entries have sorted portable paths, a fixed 1980 timestamp and regular-file mode.
Stored ZIP entries avoid compressor-version variability. Runtime code only creates
archives in memory; it never reads or extracts a supplied archive. The archive is
limited to 32 MiB, including inventory/ZIP overhead; bundles retain the existing
128-artifact/128-MiB total limits. Advanced reports accept at most 128 baseline events.
Larger inputs remain supported by the legacy report where its existing limits allow.

The evidence DAG summary excludes `report_assets/report.css` and `report_bundle.zip`
as well as the existing presentation files. The full DAG binds the stylesheet to
report JSON and the ZIP to every non-control artifact; control files and each
manifest are regenerated canonically. The ZIP is verified by reconstruction, so
no input archive parser or extraction path is added to the runtime.

Tests: [advanced report behavior](../tests/test_v2_reports.py),
[CLI proof](../tests/test_v2_cli.py), [legacy reports](../tests/test_reports.py).

## Existing schema-2 provenance summary

`build_reports` first verifies the input bundle. For a schema-2 bundle it emits a
schema-2 `ReportDocument` containing a typed `lineage` field with:

- `dag_artifact`: the fixed local name `provenance_dag.json`;
- `evidence_sha256`: the exact canonical evidence-DAG byte hash, including final LF;
- `artifacts`, `parent_links`, and sorted declared `roots`;
- the explicit scope `evidence_excluding_reports_and_integrity_controls`.

Markdown and self-contained HTML show the artifact path, digest, counts and scope
in an **Artifact lineage and integrity** section. The renderer retains existing
escaping, requires no remote assets or scripts, and never executes saved commands.
A legacy report has no lineage summary; a schema-2 report requires one.

## Avoiding circular hashes

The evidence digest covers the DAG projected without `report.json`, `report.md`,
`report.html`, `provenance.json` and `regression.json`. The full DAG already excludes
its three integrity controls and the manifest. A baseline snapshot and thresholds
remain evidence and are included when regression is requested. Additional producer
evidence must not depend on a presentation file, since that would break the
independent evidence projection.

The report references this evidence digest and the full DAG's filename. The final
DAG then includes the report files and their parent hashes. The final manifest
hashes everything, including that DAG and its two materialized views. No report
claims to contain the full hash of a DAG that includes its own bytes.

`write_reports` preserves the explicit declarations of additional producer
artifacts, rebuilds fixed report dependencies, regenerates the controls and
publishes through the existing atomic bundle writer. Repeating it with explicit
overwrite yields identical bytes for identical inputs. A changed baseline is
captured before the evidence digest is calculated. The verifier checks the
summary against the DAG and renders JSON back to Markdown/HTML to detect divergent
views even if a caller recomputes file hashes.

To upgrade an existing legacy bundle, first verify it, assemble its evidence
without the old presentation files, add lineage, and regenerate reports. For a
legacy regression report, also omit the old `regression_baseline.json` and
`regression_thresholds.json` during this initial upgrade, then supply the original
verified baseline bundle and thresholds to `write_reports`. Unused source roots
are rejected; this API does not automatically migrate an archived baseline when
its original bundle is unavailable. Adding lineage around a schema-1 report is rejected; it must not imply that an old report
already contained a verified summary.

## Limits and interpretation

The summary counts files and declared parent links, not independent scientific
evidence or confidence. It makes no claim about authorship, production detection,
or detector replay. Core run dependencies are rederived; extra producer lineage
is an explicit declaration. Keep the final manifest digest independently to
protect against a coherent rewrite. A saved integrity report describes publication;
run `verify_artifacts` to inspect the current bytes.

The [lineage example](../examples/artifact_lineage.py) creates real synthetic run,
oracle and V1 benchmark evidence and exercises report generation. Tests in
[artifact integration](../tests/test_artifacts.py) and
[graph contracts](../tests/test_v2_graph.py) cover parent tampering, missing parents,
version migration, external pins, deterministic identities, bounded reads and
report regeneration.
